# Ontology Format Requirements

[Spec](spec.md) · [Decisions](log.md)

## Problem Statement

Specs own behavior and design. Agent rules own working practice. No artifact
gives stable identifiers for what exists around the code: the repository, its
workspace packages, the runtimes they need, and how these connect. Agents
re-derive this topology from manifests and prose on each task.

Domain terms have the same problem. A glossary inside one spec covers only
that topic, does not name the Dart symbol for a term, and mixes definitions
with behavior. Other topics and code then drift to synonyms.

The documentation rules of this repository are adapted from a sibling
repository that keeps its own ontology. This repository needs a selective,
reviewed map that shares identifiers with another ontology only when the
meanings match. The map must not grow into a second copy of specs, rules, or
inventories.

Public identifiers drift the same way. A rename in one package keeps an old
word in another, and two words come to name one concept. A reviewer cannot
read every public name of three packages against the vocabulary by hand.

## Scope

- A flat set of YAML topic files under `ontology/` that declare domains, nodes, and typed relations with evidence.
- Canonical definitions of shared domain terms as concept nodes, with their preferred term and code symbol.
- The role division between `specs/`, `ontology/`, and `agents/rules/` plus `agents/skills/`.
- Node kinds, relation types, binding types, and interpretation limits.
- Reuse of identifiers shared with another repository's ontology.
- Decision logging and manual review of ontology changes.
- A vocabulary of the words that public identifiers use, held by concept and vocabulary nodes, and a script that checks the public API of the workspace packages against it.

## Out of Scope

- Automated validation of the graph structure, generated graphs, schema files, or CI gates. The vocabulary script checks words, symbol bindings, and paths only.
- Requirements, behavior, configuration values, version numbers, live state, credentials, or file inventories. A list of public API members is generated by the vocabulary script and is not kept in the ontology.
- Package dependency-direction policy, which [Project Architecture](../architecture/requirements.md) owns.
- Lifecycle behavior, which the [runtime lifecycle topic](../runtime/lifecycle/requirements.md) owns.

## User Stories

- <a id="r-us-ont-fmt-001"></a>**R-US-ONT-FMT-001** — As a developer or agent, I want one reviewed map of the repository, its packages, and their runtimes with links to the owning specs, so that I can find what a change touches without re-deriving the topology.
- <a id="r-us-ont-fmt-002"></a>**R-US-ONT-FMT-002** — As a maintainer, I want a clear ownership split between specs, ontology, and agent rules, so that each fact lives in exactly one place.
- <a id="r-us-ont-fmt-003"></a>**R-US-ONT-FMT-003** — As a developer or agent, I want each domain term defined once with its preferred word and its Dart symbol, so that specs, code, and prose use one word for one meaning.
- <a id="r-us-ont-fmt-004"></a>**R-US-ONT-FMT-004** — As a maintainer, I want every word of a public identifier traced to one declared node, so that the public API does not drift to synonyms.

## Use Cases

- <a id="r-uc-ont-fmt-001"></a>**R-UC-ONT-FMT-001** — Route a piece of information
  - Actor: author or agent
  - Trigger: new information about the system needs recording
  - Preconditions: the kind of information is known
  - Main flow: behavior, contracts, and rationale go to a spec. Stable identity and typed connections go to the ontology. Patterns, pitfalls, and procedures go to rules or skills.
  - Alternative flows: a verified mismatch between spec and code goes to the topic's `gap.md`, not to an ontology edge
  - Postconditions: the information has one owner, and other artifacts link to it
- <a id="r-uc-ont-fmt-002"></a>**R-UC-ONT-FMT-002** — Declare a node or relation
  - Actor: ontology author
  - Trigger: a repository, package, platform, or connection needs a stable identifier
  - Preconditions: an owning spec or manifest exists in this repository
  - Main flow: the author adds a uniquely identified node, or an edge with evidence and bindings to existing files. The edge stays with its source node.
  - Alternative flows: if only a prose claim exists, the author does not add it
  - Postconditions: every node and edge **MUST** resolve to existing repository files
- <a id="r-uc-ont-fmt-003"></a>**R-UC-ONT-FMT-003** — Align an ID with another ontology
  - Actor: ontology author
  - Trigger: a node resembles a node in another repository's ontology
  - Preconditions: both meanings are known
  - Main flow: the author reuses the ID only when the meaning matches. Otherwise the author chooses a repository-native ID.
  - Alternative flows: when meanings diverge later, the author introduces a new ID instead of changing the shared one
  - Postconditions: a shared ID **MUST** denote the same logical object in both repositories
- <a id="r-uc-ont-fmt-004"></a>**R-UC-ONT-FMT-004** — Interpret a relation
  - Actor: reader or agent
  - Trigger: an edge is used to answer an impact or ownership question
  - Preconditions: the type of the edge is known
  - Main flow: the reader treats the edge as a declared, selective relationship and confirms the claim in its owning source
  - Alternative flows: the reader treats the absence of an edge as unknown, not as prohibition
  - Postconditions: no cardinality, runtime, version, or health claim is derived from an edge alone
- <a id="r-uc-ont-fmt-005"></a>**R-UC-ONT-FMT-005** — Record and review an ontology change
  - Actor: ontology author and reviewer
  - Trigger: an ontology change is proposed
  - Preconditions: no validator checks the graph structure
  - Main flow: the reviewer applies the manual checklist. A change to meaning, classification, ownership, ID alignment, or vocabulary adds a decision entry.
  - Alternative flows: typo fixes and evidence updates need no entry
  - Postconditions: unique IDs, resolvable references, and recorded rationale hold at merge
- <a id="r-uc-ont-fmt-006"></a>**R-UC-ONT-FMT-006** — Define a domain concept
  - Actor: ontology author
  - Trigger: a spec needs a term that more than one section or topic uses
  - Preconditions: a spec section owns the behavior of the term
  - Main flow: the author adds a `concept` node with a `term`, an identity-only definition, a `spec` binding, and a `file` binding with `symbol` when a public Dart type names the concept. Specs link the node instead of redefining the term.
  - Alternative flows: a definition clause that states behavior moves to the owning spec first; a concept without a public type has no `symbol`
  - Postconditions: each concept **MUST** have one term and one meaning, and its behavior **MUST** remain in the bound spec
- <a id="r-uc-ont-fmt-007"></a>**R-UC-ONT-FMT-007** — Check the vocabulary of the public API
  - Actor: author, reviewer, or agent
  - Trigger: a change adds, renames, or removes a public identifier, or edits an `identifiers` or `avoid` list
  - Preconditions: `flutter pub get` has run at the workspace root
  - Main flow: the vocabulary script resolves the export namespaces of the public libraries and splits each public identifier into words. Each word **MUST** appear in the `identifiers` of a concept or vocabulary node. No word **MUST** appear in an `avoid` list. Each `symbol` of a `file` binding **MUST** name a public declaration of that file, and each binding and evidence path **MUST** exist.
  - Alternative flows: a new word goes to the node whose meaning it has, or a new node; a word with two meanings goes to both nodes; with `--prose`, an avoided word in specs, READMEs, or package docs outside decision logs and research notes is also reported
  - Postconditions: the script exits with 0, and the ontology names every word of the public API

## Verification

- <a id="v-l-ont-fmt-001"></a>**V-L-ONT-FMT-001** `[lint]` Given this spec topic, when the spec validator runs, then the triad shape, metadata, IDs, and relative links pass. Covers: R-US-ONT-FMT-002.
- <a id="v-a-ont-fmt-001"></a>**V-A-ONT-FMT-001** `[approval]` Given an ontology change, when a reviewer applies the manual checklist, then the YAML parses, IDs are unique, edge endpoints exist, and every evidence and binding path resolves to an existing file in this repository. Covers: R-US-ONT-FMT-001, R-UC-ONT-FMT-002, R-UC-ONT-FMT-005.
- <a id="v-a-ont-fmt-002"></a>**V-A-ONT-FMT-002** `[approval]` Given an ontology change, when a reviewer inspects it, then it contains no requirement, behavior, config value, version, live state, or inventory, and no path outside this repository. Covers: R-US-ONT-FMT-002, R-UC-ONT-FMT-001, R-UC-ONT-FMT-004.
- <a id="v-a-ont-fmt-003"></a>**V-A-ONT-FMT-003** `[approval]` Given a node whose ID also exists in another repository's ontology, when a reviewer compares meanings, then they match, and a change to such an ID has a decision entry. Covers: R-UC-ONT-FMT-003, R-UC-ONT-FMT-005.
- <a id="v-l-ont-fmt-002"></a>**V-L-ONT-FMT-002** `[lint]` Given the public libraries of the workspace packages and the ontology, when `agents/scripts/check_vocabulary.dart` runs, then every word of a public identifier is in some `identifiers` list, no word is avoided or in conflict, and every symbol binding and path resolves. Covers: R-US-ONT-FMT-003, R-US-ONT-FMT-004, R-UC-ONT-FMT-007.
- <a id="v-a-ont-fmt-004"></a>**V-A-ONT-FMT-004** `[approval]` Given a changed `concept` node, when a reviewer inspects it, then it has a `term`, a definition without behavior, a `spec` binding, and only symbols that the bound file declares. Covers: R-US-ONT-FMT-003, R-UC-ONT-FMT-006.
