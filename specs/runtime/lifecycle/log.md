# Runtime Lifecycle Decision Log

## [2026-09-08] decision | Ground the contract in an explicit paper adaptation

- Context: Review found lifecycle violations that pass the existing tests. The original notes mix the paper's model, Dart extensions, and excluded features, leaving no precise conformance boundary for formal verification.
- Decision: Use the supplied paper as the conceptual source, define the selected Dart profile in requirements and architecture, and record verified implementation deviations separately. Use tailored arc42 sections, a C4 component view, and ADR-inspired decision records.
- Consequences: Formal models and regression tests have a shared contract and source mapping. Paper theorems cannot be claimed for Dart extensions without checking assumptions and implementation correspondence; executable formal verification remains separate work.
- References: [Paper research](researches/spatiotemporal-composability.researches.md), [requirements](requirements.md), [spec](spec.md), gaps.

## [2026-11-02] decision | Clarify lifecycle ownership boundaries

- Context: Spec review found Flutter widget-scope ownership specified in both lifecycle and architecture, an initial-failure outcome that disagreed with the state diagram, untested requirements, and two readings of post-closure acquisition ownership.
- Decision: Architecture AR-UI criteria own widget-scope behavior; lifecycle owns core scope semantics. A failing activation started by `use` unregisters. An acquisition pending at closure is released once on completion and never transfers to the committed node. V-T-RT-LC-001/002/003/004 add assertions for these and for no-reactivation and retry suppression.
- Consequences: Flutter widget tests are evidence for V-T-AR-UI-*, not V-T-RT-LC-006. New regression rows are missing until tests land; probes show current behavior conforms for initial failure, no-reactivation, and retry suppression.
- References: [requirements](requirements.md), [spec](spec.md), gaps, [architecture](../../architecture/spec.md#flutter-integration).

## [2026-11-02] decision | Make andThen sequential and add provided

- Context: Modeling a production session scope showed `andThen` silently overlapping independent steps, contrary to its name, and each "acquire then publish" step needing a hand-declared `flatMap` shape.
- Decision: `andThen` always sequences; overlap remains opt-in through `zipWith` and `all`. `Component.provided` publishes a result under a key with a derived shape, `P(c) ∪ {k}`.
- Consequences: Breaking change for code relying on `andThen` overlap; concurrency intent is visible at the call site. Common provision steps no longer bypass shape derivation through `flatMap`.
- References: [spec](spec.md#shape-algebra), [composition](spec.md#composition-and-concurrency), [requirements](requirements.md).

## [2026-11-02] decision | Express laziness as a memoized resource type

- Context: A production session registers about 180 lazy singletons. Hidden lazy lookup would make `get` acquire resources and fail outside activation, obscuring lifetimes.
- Decision: Follow the functional memoize convention (`F<F<A>>`): `lazy(resource)` returns `Component<Lazy<A>>`. Lookup stays pure; `Lazy.get` acquires once, does not cache failure, and is rejected after release. The holder's own release owns any acquisition and awaits in-flight work.
- Consequences: Consumers see laziness in the type and call `get()`. No binding or reconciliation semantics change. Dependencies must be resolved during activation to stay tracked.
- References: [spec](spec.md#memoized-resources), [requirements](requirements.md), [README](../../../packages/fp_di/README.md).

## [2026-11-02] decision | Specify cooperative cancellation for disposal during setup

- Context: Modeling login, logout during session setup, and another login showed correct isolation but no way to stop pending work: disposal waits behind the in-flight transaction, the old session commits briefly, and a stalled acquisition blocks all mutations.
- Decision: Give each activation episode a read-only `CancellationSignal` on `Context`, completed synchronously at the disposal request, on activation failure, and when deactivation begins. A disposal-requested activation never commits; it rolls back after settlement and fails with `ActivationCancelled`. Cancellation stays cooperative; acquisition remains uncancelable once a lease is returned, following the uncancelable-acquire convention of functional resource libraries.
- Consequences: Adapters that observe the signal make logout prompt; ignoring adapters keep current behavior. `DiError` gains `ActivationCancelled`. Implementation is pending in G-RT-LC-005.
- References: [spec](spec.md#cancellation), [requirements](requirements.md), gap.

## [2026-11-02] decision | Bound cancellation by queue order and host sequencing

- Context: The cancellation entry above framed logout as not delaying the next login. Letting the next setup overlap the old rollback would require old inverses and new effects to commute (Definition 19); global inverses such as clearing WebView cookies do not, and host login effects run outside the queue.
- Decision: Refine the previous decision. Cancellation only shortens the cancelled prefix; its rollback keeps FIFO position before later mutations (R-UC-RT-LC-008). Hosts MUST await the old disposal before external login effects when old inverses touch shared non-identity-keyed state, or make those inverses identity-keyed.
- Consequences: Account switching is bounded by cooperative settlement plus rollback rather than unbounded setup time, and stays safe without independence assumptions. The host obligation is documented, not enforced by the runtime.
- References: [spec](spec.md#cancellation), [requirements](requirements.md).

## [2026-11-02] decision | Extend cancellation through checkpoints and the effect layer

- Context: A `Context`-only signal is unreachable from `acquire(Resource.make(...))`, so cooperative cancellation forced imperative components and lost derived shapes. A dependency key would mix cancellation into reconciliation; a full interruption algebra (masks, race, timeout) has no current use.
- Decision: Keep the shape algebra unchanged. The interpreter checks the episode signal at every combinator boundary and before each primitive; `Effect.cancellable`/`Resource.cancellable` receive the signal (`Effect<A> ≅ Signal → Future<Lease<A>>`), and `lazy` passes its owner's signal. Laws: shape invariance, monotonicity, prefix, atomic primitive, forward-only.
- Consequences: Uncooperative adapters stop the activation at the next boundary; cooperative ones stop sooner. Interruption combinators remain future work requiring a new decision.
- References: [spec](spec.md#cancellation), [requirements](requirements.md).

## [2026-11-02] decision | Structure cancellation as a signal tree

- Context: Review found three holes in the cancellation design: provider withdrawal did not reach an in-flight dependent (P→C deadlock), `Effect.flatMap` rolls back its first stage before the runtime sees the failure (circular wait with a signal-stopped worker), and an episode-wide failure trigger would cancel siblings even when a body catches the failure. Dart future listeners also run after the synchronous state change.
- Decision: Each episode has a root signal; `zipWith`/`branch` and composite effects derive child signals completed by local failure before that scope's first inverse (law: signal before inverse). Withdrawal requests cancel in-flight observers transitively and leave them dormant. Signals guarantee state, not listener order; ordering is expressed by composition. Hosts report cleanup issues attached to cancellation.
- Consequences: Library combinators are bound by the same rules as adapters. No synchronous cancellation hook is offered.
- References: [spec](spec.md#cancellation), [requirements](requirements.md), gap.

## [2026-11-02] decision | Close cancellation gaps for root failures, livelock, and parallel rollback

- Context: A second review found that the episode root and `map` roll back without a region signal, that a withdrawal-cancelled dependent can reactivate while the withdrawal waits in the queue, that `NoStepAfterCancel` contradicted caught-failure isolation, and that the prefix law does not describe parallel branches.
- Decision: Every rollback site is a failure region, including the root and composite `map`. Withdrawal-cancelled nodes enter `awaitingWithdrawal` until that withdrawal finishes; public lookup stays unchanged. Checkpoints and `NoStepAfterCancel` apply to the cancelled region and its descendants. Rollback follows a down-set law: reverse declaration-order linearization of the completed down-set.
- Consequences: Removing a withdrawal-requested provider from lookup was rejected because it would expose an uncommitted change. The down-set law keeps the sequential prefix law as its chain case.
- References: [spec](spec.md#cancellation), [requirements](requirements.md), [formal](../../verification/formal/spec.md#properties).

## [2026-11-02] decision | Rename Lazy.get to Lazy.force and define one lifecycle vocabulary

- Context: `DiContext.get` is a synchronous lookup, while `Lazy.get` started an asynchronous acquisition. Specs also used `scope` for failure handling and mixed unload, leave, and deactivate for one concept.
- Decision: `Lazy.force()` replaces `Lazy.get()`, following the functional `force` convention for memoized values. The lifecycle [Glossary](spec.md#glossary) owns the vocabulary; failure handling uses `failure region`. `lazy` was unreleased, so no deprecation path is kept.
- Consequences: Other topics link the glossary instead of redefining terms. The `use`/`install` alias and the `Context.get`/`require` duplicate stay for compatibility.
- References: [spec](spec.md#glossary), [memoized resources](spec.md#memoized-resources).

## [2026-11-03] decision | Add shape-preserving acquireWith and lazyWith; name the missing keys of an inactive handle

- Context: A developer-experience review found that the common case "acquire a resource from a resolved value" required `flatMap` with a manual shape. Omitting `inject` silently made the component unanalyzable. `InactiveComponent` also did not name the key that the component waited for.
- Decision: `Component.acquireWith` and `Component.lazyWith` take a `Resource`-returning continuation and keep the source shape. A `Resource` cannot read or publish keys, so the shape stays derivable. `InactiveComponent.missing` lists the gating keys that do not resolve; it is empty for a failed or disposed component.
- Consequences: `flatMap` remains for continuations that choose a component. `InactiveComponent` loses its `const` constructor. Examples and the README teach `provided`, `acquireWith`, and `lazyWith` first.
- References: [shape algebra](spec.md#shape-algebra), [memoized resources](spec.md#memoized-resources).

## [2026-11-03] decision | Move vocabulary ownership from the Glossary to the ontology

- Context: The 2026-11-02 decision made the lifecycle Glossary the owner of the vocabulary. The ontology now defines concepts with preferred terms and code symbols.
- Decision: The [lifecycle ontology](../../../ontology/lifecycle.yml) owns the definitions. The `Glossary` heading stays as a pointer, so existing links resolve. This spec keeps the behavior of each concept.
- Consequences: A term change edits the ontology and needs an ontology decision entry. Definitions no longer carry ordering; the Runtime Behavior sections state it.
- Supersedes: [Rename Lazy.get to Lazy.force and define one lifecycle vocabulary](#2026-11-02-decision--rename-lazyget-to-lazyforce-and-define-one-lifecycle-vocabulary)
- References: [ontology decision](../../../ontology/log.md).

## [2026-11-03] decision | Remove discovery mode; require declared shapes

- Context: Discovery mode kept the 0.1 behavior for a `Component.imperative` body without `inject`. One such body made the whole tree unanalyzable, disabled `zipWith` concurrency, and failed with a missing-dependency error instead of waiting. The packages are unpublished, so no compatibility duty remains.
- Decision: `Component.imperative` requires `inject`. `flatMap` defaults to an empty declaration. The `Component.analyzable` getter and runtime discovery are removed. The runtime verifies every declaration against the run. A missing required external key always leaves the node dormant.
- Consequences: Omitting `inject` is a compile-time error, so callers migrate once. An imperative body can overlap with an independent `zipWith` side; a body that touches shared state outside its shape needs `ordered: true`. G-RT-LC-003 no longer applies and is removed. `MissingDependency` remains for a composed right read that a conditional left provider leaves missing.
- References: [shape algebra](spec.md#shape-algebra), [composition and concurrency](spec.md#composition-and-concurrency), [reconciliation](spec.md#reconciliation-and-stability).

## [2026-11-06] decision | Add Module batch install with atomic failure and record-form requireN

- Context: A package needs to export a bundle of independent components. `Component.all` makes one all-or-nothing node, so one member that waits for a key blocks every sibling. Installing members with separate `use` calls repeats reconciliation and leaves a partial install after a failure. A one-key `require` forces repeated `require` and `zipWith` to read several keys.
- Decision: `Module` is an immutable ordered list of components. `DiContext.useModule` creates and activates each member in order inside one mutation and reconciles once, so each member stays its own node and forward references resolve. Dormancy is not failure. A throw in the activation of any member makes the install atomic, and the outcome does not depend on member order: the runtime deactivates and unregisters every node of the call in reverse order and rethrows, with cleanup issues attached to an `ActivationFailure`. The runtime captures the failure of a member that first activates during the closing reconciliation, so a forward reference cannot turn a failure into a silent partial install. A component outside the module that the module wakes keeps the reconciliation rule, and a reconcile after the rollback leaves it dormant. `ModuleHandle.dispose` deactivates in reverse install order and aggregates issues. Duplicate keys follow `use`. The application chooses members with plain Dart; the runtime adds no profile concept. `Component.require2` to `require8` yield a record in key order with a derived shape, and `mapN` and `acquireWithN` spread it into positional arguments, following the functional product-type convention. `Component.require` stays the one-key form and there is no `require1`.
- Consequences: Packages compose bundles without sharing a node, and a failed install leaves no registration. Listeners can see availability changes of members that activated before the failure. `Module` is a new term and has no ontology concept yet. Shape memoization, which bounds the cost of deep `andThen` chains, is recorded in the shape algebra; the remaining quadratic cost of `Component.all` is G-RT-LC-006.
- References: [spec](spec.md#module-and-batch-install), [shape algebra](spec.md#shape-algebra), [requirements](requirements.md), gap.

## [2026-11-06] decision | Expose per-member handles on ModuleHandle and add Component.make

- Context: A consumer that installs a module needs to replace or withdraw one member, for example a test that replaces a key which a member provides. `ModuleHandle` could only dispose every member. `Component.pure(value)` evaluates its argument when the component is built, so a registration list that holds `Component.pure(Foo())` constructs every `Foo` before a profile filter drops any entry.
- Decision: `ModuleHandle.members` lists one `ComponentHandle` for each member in install order. A member handle shares the code of the handle that `use` returns, so reading, `isActive`, and disposal have one meaning. `ModuleHandle.dispose` skips members that their own handles already disposed and keeps the single mutation, reverse order, one reconciliation, and one aggregated `CleanupFailure`. `Component.make(create)` is a zero-dependency constructor with an empty derived shape. It calls `create` on each activation and never at construction, and `create` MAY be asynchronous. It is the zero-key member of the `require` and `requireN` family. A `require0` was rejected because `make` takes a factory, not keys, and a second name for the same shape adds surface without meaning.
- Consequences: A consumer can keep module installation atomic and still replace one member. Disposing a member that other members depend on makes those members dormant. They activate again when another component provides the key. `Component.make` changes no existing behavior, and `Component.pure` stays for values that already exist.
- References: [spec](spec.md#module-and-batch-install), [shape algebra](spec.md#shape-algebra), [requirements](requirements.md).

## [2026-11-06] decision | Activate module members by dependency, concurrently

- Context: `useModule` activated members one after another. An application moves slow asynchronous initialization into resources whose `acquire` completes only when ready. Sequential activation adds their latencies. One connectivity probe alone adds about 650 ms. The application ran these initializations in `Future.wait` before.
- Decision: `useModule` creates every member node in install order, builds a dependency graph from the declared shapes, and starts a member when each member that provides a key it injects or watches has settled. A settled member is committed or dormant, so a dormant provider cannot block a dependent. Independent members overlap like the sides of `zipWith`. Each member publishes its providers when its own activation succeeds, so the commit order of independent members follows completion order and is not deterministic. A provider always commits before a dependent starts. `Module(components, {name, ordered = false})` adds a synthetic edge from each member to the previous member of its module, which restores the sequential behavior for bodies that touch shared state outside their shape. `Module.all` and `+` keep the flag of each source module for its own members. Members that provide one key activate in install order, so the later member fails with `DuplicateProvider` as before. A dependency cycle makes the runtime start the first unstarted member in install order. After a failure the runtime starts no further member, waits for every member in flight, rolls back every created node in reverse install order, and rethrows the failure of the first failed member in install order. Teardown, member handles, the closing reconcile, and the rules for outside nodes stay unchanged.
- Consequences: Startup takes the length of the slowest dependency chain. Members that read or write outside their declared shape need `ordered: true`. The runtime issues no cancellation to a sibling in flight, because the activation commit has no cancellation check and G-RT-LC-005 records the missing signal. A module install is not yet a failure region. The state of a node, bindings, and dependency tracking tolerate overlap across nodes, because each node has its own activation context and the commit of one node runs without an await between its duplicate check and its binding writes. `Module` exposes `chainsToPrevious` for `useModule`, a public method that is not part of the contract. The Lazy TLC scenarios do not apply, because `Component.lazy`, `Lazy`, and `runCleanups` do not change.
- References: [spec](spec.md#module-and-batch-install), [requirements](requirements.md), gap.

## [2026-11-06] decision | Rename the key type to DiKey

- Context: `package:flutter/widgets.dart` exports its own `Key`. Flutter code that imported both libraries had to write `hide Key` or import `fp_di` with a prefix. Readers also confused the key qualifier with the `named` diagnostic label.
- Decision: The typed binding address is `DiKey<T>`, in line with `DiContext`, `DiChange`, and `DiError`. The non-generic `DependencyKey` interface and the shape sets keep their names. No `Key` alias remains, because an alias keeps the collision.
- Consequences: Breaking change for every caller that names a key. Vendored copies of `fp_di` need the rename. The ontology adds the dependency key concept with the `DiKey` symbol.
- References: [spec](spec.md#constraints--solution-strategy), [ontology](../../../ontology/lifecycle.yml).

## [2026-11-06] decision | Name the scope DiScope and the activation context DiContext

- Context: The scope type was `DiContext` and the activation interface was `Context`. Readers could not tell the two apart by name. In Flutter, `context` names a `BuildContext`, so `FpDiScope(context: ...)` also misled.
- Decision: The scope type is `DiScope`. The activation interface is `DiContext`. `DisposedContext` is `DisposedScope`. `FpDiScope` takes `scope:`. No aliases remain.
- Consequences: Breaking change. Entries before this one use `DiContext` for the scope and `Context` for the activation context. Code that names the old scope type fails to compile, because the new `DiContext` has no `root`, `use`, or `dispose`. Vendored copies need both renames. Private runtime fields keep their names.
- References: [spec](spec.md#scope-ownership), [ontology](../../../ontology/lifecycle.yml), [ontology log](../../../ontology/log.md).

## [2026-11-06] decision | Name the producer side publish

- Context: In ZIO and Effect-TS, `provide` supplies dependencies to a consumer and removes a requirement. In `fp_di`, `provide` meant that a producer adds a binding to a scope. Readers who know functional effect libraries read the direction backwards.
- Decision: The producer verb is `publish`: `Component.publish`, `.published()`, `DiContext.publish`, and the shape set `publishes`. The nouns follow: the binding owner is a publisher and a staged binding is a publication. `DuplicateProvider` is `DuplicatePublisher`, `UndeclaredProvision` is `UndeclaredPublication`, and `DiChangeKind.providerAvailable` and `providerUnavailable` are `publisherAvailable` and `publisherUnavailable`. No aliases remain.
- Consequences: Breaking change for every producer call and every shape declaration. Entries before this one use provide, provider, and provision. The paper mapping keeps the paper's own terms in its source column. Private runtime names follow the new verbs. Vendored copies need the rename.
- References: [spec](spec.md#shape-algebra), [ontology](../../../ontology/lifecycle.yml), [ontology log](../../../ontology/log.md).

## [2026-11-06] decision | Make Resource the only acquire/release type

- Context: `Effect` and `Resource` had the same constructors and behavior, and no test, example, or known consumer used `Effect`, `Component.perform`, or `DiContext.runEffect`. In the source paper, an effect is a reversible transformation with a witnessed inverse. In ZIO, Effect-TS, and fpdart 2.0.0-dev.3 (`Effect<E, L, R>`), an effect is any computation, so the public type collided in name and in meaning. `DiContext.effect` also shared the word but took an installer, not an `Effect`.
- Decision: `Resource` is the only public acquire/release type, and `Lease` replaces `EffectLease`. `Effect`, `Component.perform`, and `DiContext.runEffect` are removed. The `DiContext` methods take the names of their `Component` constructors: `DiContext.acquire` replaces `DiContext.resource`, and `DiContext.reversible` replaces `DiContext.effect`. `reversible` stays synchronous, so an imperative body records an inverse without an await. The planned cancellable constructor is `Resource.cancellable` only.
- Consequences: The paper's effect stays a design concept. A value-yielding effect is a `Resource`, and a value-free effect is a `reversible` installer. Behavior, shapes, and cleanup order do not change. The Lazy TLC scenarios do not apply, because only the lease type name inside `Lazy` changes. Earlier entries use the old names.
- References: [spec](spec.md#cancellation), [paper mapping](researches/spatiotemporal-composability.researches.md), [lease.dart](../../../packages/fp_di/lib/src/model/lease.dart).

## [2026-11-06] decision | Construct a resource with the unnamed constructor

- Context: `Resource.make` followed the `Effect.make` pair and the cats-effect name. After `Effect` was removed, `Resource` had one public constructor, and Dart uses the unnamed constructor for the primary way to create a value.
- Decision: `Resource(acquire:, release:)` replaces `Resource.make(acquire:, release:)`. No alias remains. A later cancellable form takes a named constructor.
- Consequences: `Component.make` keeps its name, because it creates a value on activation and takes no release. Earlier entries use `Resource.make`.
- References: [lease.dart](../../../packages/fp_di/lib/src/model/lease.dart), [spec](spec.md#cancellation).

## [2026-11-06] decision | Name the zero-key constructor and zip records of components

- Context: Every component started from a static member such as `Component.make`, while Dart uses the unnamed constructor for the primary way to create a value. Combining components needed `zipWith` with a combine function, and `require2` to `require8` covered keys only. Dart 3 combines a record of futures with `(a, b).wait`.
- Decision: `Component(create)` replaces `Component.make(create)` with the same behavior. A record of 2 to 8 components has a `zip` getter that is a left-nested `zipWith` without `ordered`. The `zip` extensions take the names `ComponentRecord2` to `ComponentRecord8`, after `FutureRecord2`, and the extensions on a component of a record become `ComponentOfRecord2` to `ComponentOfRecord8`. `requireN` stays as the one-node form for keys only. The other constructors stay static, because a Dart constructor cannot declare type parameters, so `maybe`, `requireN`, `lazy`, and `all` cannot be constructors.
- Consequences: No shape law changes, because `zip` is `zipWith` composition. A record of requires has the `requireN` shape but builds one node for each member. The Lazy TLC scenarios do not apply, because no lifecycle boundary changes. Earlier entries use `Component.make`.
- References: [spec](spec.md#shape-algebra), [requirements](requirements.md), [component.dart](../../../packages/fp_di/lib/src/model/component.dart).

## [2026-11-06] decision | Define releases only through Resource

- Context: The README example published a database built at construction time and closed it with `onDispose`. Each teardown closed the one shared object, and a reinstall published the closed object again. `onDispose` and `Component.reversible` let a component define a release, so the graph description also carried lifetimes.
- Decision: A `Component` describes graph structure, and a `Resource` describes a lifetime. `Component.onDispose` and `Component.reversible` are removed. A release enters a component only through `Component.acquire`, `acquireWith`, `acquireWithN`, `lazy`, or `lazyWith`. `Component.imperative` keeps `cleanup` and `DiContext.reversible` as the declared escape hatch, and `DiContext.reversible` stays synchronous.
- Consequences: A value that needs a release is created on activation in the common path. Wrapping an existing value in a `Resource` can still release a shared object; the README warns against it. Release order is unchanged, because an `acquireWith` release also runs before the inverses of its source. `acquireWith` awaits its acquisition, while `onDispose` registered synchronously, so an imperative body that needs a synchronous registration uses `DiContext.reversible`. The Lazy TLC scenarios do not apply, because `Lazy` and `runCleanups` do not change.
- References: [spec](spec.md#building-blocks), [README](../../../packages/fp_di/README.md), [component.dart](../../../packages/fp_di/lib/src/model/component.dart).

## [2026-11-06] decision | Require the producer key

- Context: `published`, `Component.publish`, and `DiContext.publish` defaulted their key to `DiKey<A>()` of the result type. A component built from an implementation type therefore published a key that no consumer of the port required, and the consumer stayed dormant without an error. The main application already passed an explicit key at 1277 of 1278 `published` call sites.
- Decision: The producer key is required at `published`, `Component.publish`, and `DiContext.publish`. The parameter stays named, as `key:`. `DiScope.overrideValue` is removed, because with a required key it equals `DiScope.override(key, value)`. Consumer keys of `require`, `maybe`, `get`, and `requireN` keep the `DiKey<T>()` default.
- Consequences: A key of a port type needs a component of that type, so a mismatch between an implementation result and a port key is a compile error. Every publishing node has an explicit key that diagnostics can use as a label. Shapes, lookup, and lifecycle do not change. The Lazy TLC scenarios do not apply.
- References: [spec](spec.md#shape-algebra), [component.dart](../../../packages/fp_di/lib/src/model/component.dart), [context.dart](../../../packages/fp_di/lib/src/model/context.dart).

## [2026-11-06] decision | Build a component from a resource

- Context: A component had three sources with overlapping meanings. `Component.pure(x)` returned a value that existed at construction. `Component(create)` called a factory on each activation. `Component.acquire(resource)` acquired a value with a release. An author had to choose a constructor by whether the value needed a release. `pure(x)` equaled `Component(() => x)` for a value that already existed. The main application used `pure` in no production code and used `Component(create)` once. The earlier description of `Component(create)` as the zero-key member of the `require` family treated a source as a special case of a read.
- Decision: A component is a graph shape plus a `Resource`. The unnamed constructor is `Component(resource)` and replaces `Component.acquire`. `Component(create)` and `Component.pure` are removed. The `release` of `Resource` is optional, and a lease without a release releases nothing. `map` keeps the release of its source, like `Resource.map`, and `acquireWith` adds a lifetime, like `Resource.flatMap`. `Component.publish` stays for a value that exists before activation. A node is a component installed in a `DiScope`. The zero-key `require` description is withdrawn: a source reads no key, and a derived component reads keys and activates again when their publishers change.
- Consequences: Every value that enters the graph comes from a `Resource`, with or without a release. A constant becomes `Component(Resource(acquire: () => x))`. A release-free resource records a no-op inverse, so its teardown order matches a resource with a release. `Component.all` of an empty list still uses a private constant component. `Component.lazy` routes through the same private acquire node, and `Lazy` and `runCleanups` do not change, so the Lazy TLC scenarios do not apply.
- References: [spec](spec.md#shape-algebra), [requirements](requirements.md), [README](../../../packages/fp_di/README.md), [component.dart](../../../packages/fp_di/lib/src/model/component.dart), [lease.dart](../../../packages/fp_di/lib/src/model/lease.dart).

## [2026-11-06] decision | Split a component into a source and its publications

- Context: A component mixed three concerns: the keys it read, the lifetime of its value, and the composition of other components. `zipWith`, `andThen`, `all`, `flatMap`, and `Component.imperative` let one component run several sub-components, publish several values, run branches concurrently, and declare shapes by hand. The main application used none of them in production code: every component read keys, built a value, and published it.
- Decision: A `Resource` states creation and an optional release. A `Graph` states the keys a component reads and the steps that build its value; it never publishes. A `Component` is a source, which is a `Resource` or a `Graph`, plus its published keys. `Component(resource)` makes a source component, and `Component(graph)` makes a dependent component. `Graph.require`, `maybe`, `require2` to `require8`, `map`, `acquireWith`, `lazyWith`, `mapN`, `acquireWithN`, and a record `zip` replace the `Component` reads and combinators. `Resource.lazy()` replaces `Component.lazy`. `zipWith`, `andThen`, `all`, `flatMap`, `concurrent`, `Component.imperative`, the public activation context, `UndeclaredDependency`, and `UndeclaredPublication` are removed.
- Consequences: Every shape is derived, so no declaration can drift. The steps of one component run in order, and independent work overlaps only across module members. A graph reads every key of its shape, which resolves G-RT-LC-004. No caller can capture the activation context, which resolves G-RT-LC-001. `Component.all` no longer exists, which retires G-RT-LC-006. One component can no longer publish the values of several steps, and a module commits its members one by one, so several values become visible together only as one published record; the session-scope probe records this loss. A duplicate publication now rolls back the acquisitions made before it. R-UC-RT-LC-005, R-UC-RT-LC-015, V-T-RT-LC-005, V-T-RT-LC-015, and V-T-VR-TEST-002 keep their IDs with the new sequential and module meaning. The durable invariant of concurrent `zipWith` branches is replaced by concurrent module members. `Lazy` and `runCleanups` do not change, so the Lazy TLC scenarios do not apply.
- References: [spec](spec.md#shape-algebra), [requirements](requirements.md), gap, [README](../../../packages/fp_di/README.md), [graph.dart, now dependency.dart](../../../packages/fp_di/lib/src/model/dependency.dart), [component.dart](../../../packages/fp_di/lib/src/model/component.dart), [formal verification](../../verification/formal/spec.md).

## [2026-11-08] decision | Rename Graph to Dependency

- Context: The type that states the keys a component reads was named `Graph`. The prose of this topic also uses "graph" for the publisher graph of a scope and for the dependency graph of a module, so one word had two meanings.
- Decision: `Graph` is now `Dependency`. The library file is `dependency.dart`, the record extensions are `DependencyOfRecord2` to `DependencyOfRecord8` and `DependencyRecord2` to `DependencyRecord8`, and the hidden runner is `runDependency`. Behavior, shapes, and IDs do not change. Prose writes the type as `Dependency` in code format. A lowercase "dependency" keeps its meaning: a publisher of a key that a component reads. `DependencyKey` stays the type of one key.
- Consequences: "Graph" in this topic now names only the publisher graph and the dependency graph of a module. The type name `Dependency` is close to `DependencyKey` and to the lowercase word, so the spec and the README state the distinction. Earlier log entries keep the name `Graph`.

## [2026-11-08] decision | Observe a node and a scope without a mutation

- Context: `use` and `useModule` return while a component is dormant, and the only signs of its state were `isActive` and the `missing` keys of an `InactiveComponent` thrown by `value`. Bootstrap code could not wait for a component, and a reader could not see why a scope held no binding.
- Decision: `ComponentHandle.whenActive` completes with the value at the commit of an activation, at once for an active node, and fails with `InactiveComponent` when the node is unregistered first. A failed automatic activation leaves it pending, because a later mutation can still activate the node and `DiScope.errors` already reports the failure. `ComponentHandle.missing` returns the unresolved required keys with the computation of `InactiveComponent.missing`. `DiScope.describe()` returns a diagnostic text of the scope and its descendants, with the states `active`, `waiting`, `blocked`, and `inactive`. No read enters the mutation queue or changes `revision`.
- Consequences: A caller of `whenActive` that needs a timeout or a failure signal adds it, for example with `Future.timeout` or a listener on `errors`. A waiter future that has no listener when its node is disposed reports an uncaught error. The text of `describe` is not a stable format, so tests and tools MUST NOT parse it. R-US-RT-LC-008, R-UC-RT-LC-016, and V-T-RT-LC-016 are new.
- References: [spec](spec.md#observation), [requirements](requirements.md), [context.dart](../../../packages/fp_di/lib/src/model/context.dart), [component.dart](../../../packages/fp_di/lib/src/model/component.dart).

## [2026-11-08] decision | Remove scope overrides; every binding has a node

- Context: `DiScope.override(key, value)` added a scope-owned binding with no node. It could not replace a binding in its own scope, because a second binding of a key is rejected, so the name promised a capability that it lacked. `use(Component.value(value).published(key: key))` already gave the same shadowing, duplicate rule, and removable handle. `override` also took a value and a key in one call, so inference let a value of an unrelated type compile, and the runtime needed a separate type check and a separate handle type.
- Decision: `override` and `OverrideHandle` are removed. A value that exists before activation enters a scope only as `Component.value(value).published(key: key)`. Every binding record has a node as its publisher. A test replaces a binding by building the module with a fake, by shadowing it in a child scope, or by disposing one member and installing the fake.
- Consequences: Withdrawal, scope disposal, and `describe` have one kind of publisher. A port mismatch is a compile error for every binding. A binding in a child scope does not change what a parent node reads, so a test installs its fake in the scope of the code under test or above it. The checks of `V-T-RT-LC-006` no longer include an override type mismatch.
- References: [spec](spec.md#constraints--solution-strategy), [requirements](requirements.md), [testing notes](../../../packages/fp_di/doc/topics/declaration.md#testing), [context.dart](../../../packages/fp_di/lib/src/model/context.dart).

## [2026-11-08] decision | Declare a scope's contents and create them in initialize

- Context: `DiScope.use` and `DiScope.useModule` both registered and created components in one call, so a scope had no point where its contents were known and nothing was created yet. Any code could add a component to a live scope at any time, and the time of creation depended on when the call ran. Flutter code builds a configuration first and mounts it later.
- Decision: A scope declares its contents at creation: `DiScope([module])` for a root and `child([module])` for a child. `initialize()` creates them in one mutation with the former `useModule` semantics, and `dispose()` releases them. `use`, `useModule`, and `ModuleHandle` are removed; `DiScope.members` lists the member handles. The contents are fixed: no call adds a component to an initialized scope. A second `initialize` throws a `StateError`, `initialize` on a disposed scope throws `DisposedScope`, and a failed `initialize` rolls back and leaves the scope uninitialized so that it can retry. A child MAY initialize before its parent.
- Consequences: A publisher appears for an existing node only when an ancestor initializes later, or when a scope between the node and its publisher initializes later and shadows it. Late installation into a live scope and replacement of one member are out of scope; a new set of components is a new child scope. R-US-RT-LC-001 and R-US-RT-LC-005 lose replacement and keep withdrawal. R-UC-RT-LC-009, R-UC-RT-LC-012, and R-UC-RT-LC-014 keep their IDs with `initialize`, `members`, and declaration order in place of `useModule`, `ModuleHandle`, and install order. Two module tests are removed because an outside node can no longer be both a publisher for a member and a dependent of the module; a new test covers a descendant node that wakes in the closing reconciliation and is dormant after the rollback. A duplicate publisher now fails the whole `initialize`, because both publishers are members of one call. G-RT-LC-002 and G-RT-LC-005 were run again in the new form and still reproduce.
- References: [spec](spec.md#scope-declaration-and-initialization), [requirements](requirements.md), gap, [context.dart](../../../packages/fp_di/lib/src/model/context.dart), [declaration notes](../../../packages/fp_di/doc/topics/declaration.md#scopes-and-modules).

## [2026-11-08] decision | Edit modules as values instead of updating scopes

- Context: A fixed scope cannot change after `initialize`. A declarative `DiScope.update(module)`, which diffs a live scope against a new declaration, was considered. It needs an identity rule for members, a partial teardown order, and it brings back a live scope that changes. Applications usually declare a scope and initialize it at once, so the change belongs before the scope exists.
- Decision: `Module` gains `replacing(key, component)`, `without(key)`, and `where(test)`, which return a new module and keep the position and the ordering rule of each remaining member. A member is found by the key that it publishes, and an absent or ambiguous key is an `ArgumentError`. `Module` also gains the derived shape `publishes`, `requires`, and `observes`; `observes` contains `requires`, as `Component.observes` contains `inject`. `initialize()` completes with its scope. `DiScope.update` is not added.
- Consequences: A test replaces a member with a fake in the module value, and a reader sees which keys a module needs from its ancestors before activation. A member without a published key is reachable only through `where`. `requires` is the first input for a whole-graph check before `initialize`, which stays out of scope. R-US-RT-LC-009, R-UC-RT-LC-017, and V-T-RT-LC-017 are new.
- References: [spec](spec.md#scope-declaration-and-initialization), [shape algebra](spec.md#shape-algebra), [module.dart](../../../packages/fp_di/lib/src/model/module.dart).

## [2026-11-08] decision | Reject required keys that no declaration publishes

- Context: A component without `published(key: ...)` publishes nothing, which is valid for a listener. When the author forgot the key on an intended publisher, its consumers stayed dormant with no error, and only `describe` or `missing` showed the cause. Once the contents of every scope became fixed at creation, the runtime could see every publisher that a scope will ever have.
- Decision: Before it creates any node, `initialize` throws `UnresolvableDependency` when a member injects a key that no other member and no member declared by an ancestor publishes. Ancestors count whether or not they are initialized. A member's own publication does not count. Optional reads are not checked. The error names each member and key.
- Consequences: A forgotten key fails at once with the member and key named, so the producer key stays where it is and the mistake is still caught. Dormancy now means waiting for a declared publisher: an ancestor that has not initialized, or a withdrawn member. Tests that waited for a key that nothing declares declare it in an ancestor that never initializes. Whole-graph validation beyond this check, such as unsatisfiable cycles, stays out of scope. V-T-RT-LC-001 now also covers R-UC-RT-LC-009.
- References: [spec](spec.md#scope-declaration-and-initialization), [requirements](requirements.md), [error.dart](../../../packages/fp_di/lib/src/model/error.dart), [context.dart](../../../packages/fp_di/lib/src/model/context.dart).

## [2026-11-08] decision | Find a member handle by its key

- Context: `DiScope.members` was the only way to reach the handle of one member, so callers wrote `members[1]`. An index depends on the declaration order and changes silently when a module is edited, while `Module.replacing` and `Module.without` already find a member by the key that it publishes.
- Decision: `DiScope.member(key:)` returns the handle of the member that publishes the key, typed as the key. It throws a `StateError` before `initialize` and an `ArgumentError` when no member publishes the key. `members` stays as the declaration-order list for members that publish no key.
- Consequences: Examples and the README read handles by key and need no cast. A handle stays a view of one node, distinct from the immutable `Component` description, because one description can be declared in several scopes.
- References: [spec](spec.md#scope-declaration-and-initialization), [context.dart](../../../packages/fp_di/lib/src/model/context.dart).

## [2026-11-08] decision | Name the node type ComponentNode

- Context: The public view of a node was `ComponentHandle`. "Handle" is rare in Dart APIs, and this topic and the ontology already call the concept a node. `ComponentState` was considered for the analogy with a widget and its `State`, but a Flutter `State` is a class that developers subclass, and "state" already names the values `active`, `waiting`, `blocked`, and `inactive`. `ComponentElement` is a Flutter class name.
- Decision: `ComponentHandle` is renamed `ComponentNode`. Prose calls it a node. A `Component` is the immutable description, like a widget; a `ComponentNode` is that description created in one scope, like the element of a mounted widget.
- Consequences: The public type, the spec, and the `component_node` ontology concept use one word. Behavior does not change.

## [2026-11-08] decision | Make Dependency the only value type

- Context: `Dependency1` to `Dependency8` take `create` and `dispose` directly, so the common dependent value no longer named a `Resource`. A `Resource` then remained for a value without inputs, for lazy values, and for composing lifetimes outside the dependency graph; each of these is a `Dependency` with zero inputs or a chain step.
- Decision: `Resource`, `Lease`, `Undo`, and `Source` leave the public API. `Dependency<R>(create:, dispose:)` makes a value without inputs, `Dependency1` to `Dependency8` read one to eight keys, and a chain adds `map(create, dispose:)` and `mapN(create, dispose:)` steps; `resource` and `resourceN` are removed. `Dependency.lazy()` replaces `Resource.lazy()`: it reads the keys of the `Dependency` at activation, so they stay tracked, and runs its steps on the first `force()` against those values, owning what they create. `Component(source:)` takes a `Dependency`. The runtime keeps leases internal.
- Consequences: One vocabulary, `create` and `dispose`, covers every value. A `dispose` receives only the value of its step, so a release that needs an input keeps it in the value or reads it in another component. `lazy()` defers every step of its `Dependency`, so an eager step and a lazy step in one component are zipped. A lifetime that a library shares without keys is a function that returns a `Dependency`. R-UC-RT-LC-005, R-UC-RT-LC-007, R-UC-RT-LC-013, and their V-T criteria keep their IDs with `Dependency` in place of `Resource`. The Lazy TLC scenarios ran and pass, because the `Lazy` holder did not change.
- References: [spec](spec.md#building-blocks), [memoized resources](spec.md#memoized-resources), [dependency.dart](../../../packages/fp_di/lib/src/model/dependency.dart), [lease.dart](../../../packages/fp_di/lib/src/model/lease.dart).

## [2026-11-08] decision | Make the keys the only order and reject duplicate keys at initialize

- Context: `Module(ordered: true)` started each member after the previous one, for a need on an effect that no key shows. The flag ordered only the first `initialize`: a later reactivation ignored it, and the runtime could not check it. A token key that one member publishes and the other requires states the same need inside the graph. No user of the runtime uses the flag. A duplicate key in one scope failed only when the later member published, after both values were created, although the contents of a scope are fixed at creation.
- Decision: Remove `ordered` and `Module.chainsToPrevious`. The keys are the only order between members, and a member that needs the effect of another requires a token key. `initialize` throws `DuplicateKeyError` with the key and the member labels before it creates a node when two members of the scope publish the same key. The check at commit stays as a guard.
- Consequences: A need on an effect is part of the shape, so it holds on reactivation and teardown and shows in `describe`. `Module` no longer tracks groups, and `initialize` has one publisher for each key. The provisions of one scope are disjoint before activation, as Definition 43 of the paper requires. Callers that pass `ordered:` break.

## [2026-11-08] decision | Reconcile until stable, within a bound

- Context: G-RT-LC-002 showed that `_Runtime.reconcile` compared active targets once, before the dormant activation loop, so an optional reader missed a publisher that the same mutation activated. The reconcile model (`verification/tla/reconcile/Reconcile.tla`) reproduces this as the `SkipRecheck` counterexample to `StableTargets`. Repeating the passes alone would loop forever on optional reads that feed back into each other, which the spec does not promise to converge.
- Decision: A reconciliation repeats the rebuild and dormant passes while an activation of the previous pass changed the target of an active node, and stops after `nodes + 1` passes. When it stops without settling, it reports a `DependencyCycleError` of the stale nodes as the `cause` of an `ActivationException` on `DiScope.errors`, and the initiating mutation succeeds. A pass rebuilds only nodes whose targets changed, so `NoNeutralReload` holds.
- Consequences: G-RT-LC-002 is closed, and V-T-RT-LC-004 has regression evidence. An acyclic read graph settles within the bound; the model checks it for four topologies. Optional feedback now ends with a reported error instead of a stale view.
- References: [spec](spec.md#reconciliation-and-stability), [requirements](requirements.md), [runtime.dart](../../../packages/fp_di/lib/src/runtime/runtime.dart), [regression_test.dart](../../../packages/fp_di/test/regression_test.dart), [reconcile model](../../../verification/tla/reconcile/Reconcile.tla).

## [2026-11-08] decision | Fail initialize when its own members do not settle

- Context: The bounded reconciliation reported optional feedback that did not settle on `DiScope.errors` and let the initiating mutation succeed, even when the stale nodes were members of the `initialize` call. `UndeclaredKeyError` and `DuplicateKeyError`, the other wiring mistakes within one scope, fail `initialize`.
- Decision: When the reconciliation of an `initialize` call stops at its pass bound and a stale node is a member of that call, `initialize` throws the `DependencyCycleError.unsettled` and rolls back. Stale nodes of other scopes, such as a descendant that the call wakes, are still reported through `DiScope.errors`, and the call succeeds. This supersedes the "initiating mutation succeeds" part of [Reconcile until stable, within a bound](#2026-11-08-decision--reconcile-until-stable-within-a-bound) for members of the call.
- Consequences: Two members that read each other optionally can no longer be initialized together; a required read breaks the feedback. The reconcile model checks the rule as `UnsettledFailsInit`, and its `UnsettledSucceeds` defect violates it.
- References: [spec](spec.md#reconciliation-and-stability), [runtime.dart](../../../packages/fp_di/lib/src/runtime/runtime.dart), [regression_test.dart](../../../packages/fp_di/test/regression_test.dart), [reconcile model](../../../verification/tla/reconcile/Reconcile.tla).

## [2026-11-08] decision | Name the cancellation API after Dart and pass the token as a Dependency

- Context: The cancellation design named a `CancellationSignal` with `isCancelled` and `whenCancelled`, `Dependency.cancellable`, and `ActivationCancelledException`, and gave only a no-input `create` access to the signal. The Dart platform has no standard token type; the dart-lang package `package:async` spells `CancelableOperation` and `isCanceled`, and Flutter uses the American spelling.
- Decision: The public type is `CancellationToken` with `isCanceled` and `whenCanceled`, and the exception is `ActivationCanceledException`. `Dependency.cancellation()` is a `Dependency` that reads no key and yields the token, so any step combines it with its reads through `zip`; no `cancelable` variant of `Dependency` or `DependencyN` exists. The token lives as long as its activation: it is canceled when the disposal of the owner is requested and when the active episode starts to deactivate. Implementation proceeds in phases: owner disposal first, then withdrawal propagation, then failure regions and `Lazy`.
- Consequences: Shapes are unchanged, because the token is not a key. One API covers every arity. Owner disposal no longer commits a canceled setup, and `initialize` fails with `ActivationCanceledException`; a canceled automatic activation is not reported as a failure. G-RT-LC-005 narrows to withdrawal propagation and failure regions.
- References: [spec](spec.md#cancellation), [requirements](requirements.md), [cancellation.dart](../../../packages/fp_di/lib/src/model/cancellation.dart), [runtime.dart](../../../packages/fp_di/lib/src/runtime/runtime.dart), [cancellation_test.dart](../../../packages/fp_di/test/cancellation_test.dart), [cancellation model](../../../verification/tla/cancellation/Cancellation.tla).

## [2026-11-08] decision | Limit failure regions to the episode root and the Lazy creation

- Context: The cancellation design made every rollback site a failure region, including composite stages that catch a failure and run a fallback. The runtime has no such combinator now: the steps of one activation share one rollback list, and only a `Lazy` creation rolls back on its own. G-RT-LC-005 remained open for the failure-region part after owner disposal and withdrawal propagation were implemented.
- Decision: The failure regions are the episode root and each `Lazy` creation, a child of its owner's root. A failed step cancels the activation token before the first inverse. A `Lazy` creation receives a child token, which the owner's cancellation reaches and whose own failure leaves the owner active. A `Lazy` creation in flight when its owner is released reports `DisposedLazyException`. Each member of an `initialize` stays its own region, so a member failure still does not cancel a sibling in flight.
- Consequences: G-RT-LC-005 is closed and the lifecycle topic has no open gap, so its `gap.md` is removed. `Cancellation.tla` keeps its more general composite regions as a design check; `cancellation_test.dart` bridges its counterexamples that apply to these regions.
- References: [spec](spec.md#cancellation), [requirements](requirements.md), [runtime.dart](../../../packages/fp_di/lib/src/runtime/runtime.dart), [dependency.dart](../../../packages/fp_di/lib/src/model/dependency.dart), [cancellation_test.dart](../../../packages/fp_di/test/cancellation_test.dart).

## [2026-11-09] decision | Add set and map collection keys that reduce to plain keys

- Context: An application lists the elements of one interface by hand, for example the app scopes that start at once and those that start at the first foreground, and each element has platform and test variants. A module-built collection works without runtime support, but the element keys and the list member drift apart when the module is edited, and the shape cost grows with nested `zip` steps. A lookup of every value of a type puts the collecting component into its own list and cannot tell apart two lists of one interface.
- Decision: The runtime adds `DiSetKey<T>` and `DiMapKey<T>`. A set contribution is anonymous; a map entry is the publication of an entry key `map.entry(id)` with a `String` id, which other members read with `Dependency.require`. A reader sees the members of its scope and its ancestors, ancestors first, in declaration order; a parent does not see a child. A set read yields a `Set<T>`, a map read a `Map<String, T>`, and a map id selects the nearest available entry. Membership comes from declarations and shrinks only by disposal; a strict read waits for every member, and an optional read takes the active ones. A collection read counts in `reads`, not in `requires`, and an empty collection is valid. The runtime reduces each collection read to plain reads of member keys, each a binding of one key in one scope. A lookup by type, a list kind, and decoration are excluded.
- Consequences: Bindings, resolution, withdrawal order, scheduling, and the formal models keep their rules; the models apply through the reduction, and membership, order, and set collapse are covered by tests. `DiKey.==` accepts only a `DiKey` and compares the map key of an entry. `Dependency`, `AnyComponent`, and `Module` gain derived collection sets. A contribution to a wrong collection key is not detected, so a wiring test compares `contributes`. G-RT-LC-007 is open until the runtime implements the design.
- References: [requirements](requirements.md), [spec](spec.md#collection-keys), [collections example](../../../packages/fp_di/example/collections.dart), [key.dart](../../../packages/fp_di/lib/src/model/key.dart).

## [2026-11-09] decision | Export the shape from module values in a tooling library, without code generation

- Context: A review of an application needs the wiring of each variant as data, and a debugging session needs the chains of members that `initialize` activates one after another. A `build_runner` generator would read source, but the modules of a variant come from Dart conditionals, helper functions, and derived keys such as `map.entry(id)`; it would have to reimplement the shape algebra over syntax. The requirements exclude generated dependency typing. A separate package would add a release unit for one function.
- Decision: `package:fp_di/tooling.dart`, a library of the `fp_di` package that `fp_di.dart` does not export, provides `ShapeGraph.of(module, ancestors:)`. It reads the derived shape of module values and creates nothing. A tool script of the application imports the modules and writes `toJson()` per variant. The JSON names `format` `fp_di.shape` and `version` 1; a new field keeps the version, and a changed or removed field changes it. Edges follow the scheduling rule of `initialize`, depth is computed over strongly connected components, and the export reports unresolved and duplicate keys without throwing. Durations are excluded; a runtime trace is a separate decision.
- Consequences: No codegen and no new package. The export is exact for every variant that Dart can build, because it reads the same values as `initialize`. An application keeps a short script under `tool/`. The schema becomes a compatibility surface of the package.
- References: [requirements](requirements.md), [spec](spec.md#shape-export), [shape_graph.dart](../../../packages/fp_di/lib/src/model/shape_graph.dart), [shape_export example](../../../packages/fp_di/example/shape_export.dart), [shape_graph_test.dart](../../../packages/fp_di/test/shape_graph_test.dart).

## [2026-11-09] decision | Release a disposed scope along its reads, concurrently

- Context: Members of a module activated at the same time along their reads, but `DiScope.dispose` released every node one after another in reverse install order, so five independent releases of 100 ms took 500 ms. The paper reverts one accumulator in LIFO order without a hypothesis (Theorem 16) and pairwise independent effects in any order (Corollary 21); across components the declared reads carry the order (p. 17, §4.3.1, Theorem 63). The sequential teardown already released concurrently activated members out of their completion order, so it relied on the same independence as concurrent activation.
- Decision: `DiScope.dispose` starts the release of a node once every node that read one of its values has finished, and releases nodes that do not wait for each other at the same time. One node keeps its LIFO order. A read cycle starts the node installed last, which releases its dependents depth first. Issues follow reverse install order. The rollback of a failed `initialize`, a member disposal, and a withdrawal stay sequential. `Teardown.tla` was checked before the change. This supersedes the reverse install order of scope disposal in R-UC-RT-LC-009, R-UC-RT-LC-012, and R-UC-RT-LC-014.
- Consequences: Teardown takes as long as its slowest chain of releases. The order of releases and of `DiChange` events between unrelated nodes is no longer fixed. Two members that share an external resource without a key between them can now release at the same time; a token key orders them, as it orders their activation.
- References: [requirements](requirements.md), [spec](spec.md#composition-and-concurrency), [Teardown.tla](../../../verification/tla/teardown/Teardown.tla), [research](researches/spatiotemporal-composability.researches.md), [concurrent_teardown_test.dart](../../../packages/fp_di/test/concurrent_teardown_test.dart).

## [2026-11-09] decision | Overlap the branches of an explicit zipPar inside one component

- Context: The steps of one component ran in order, so independent work overlapped only across nodes. Two independent owned values that must become visible together as one record therefore took the sum of their latencies. The split into a source and its publications recorded that loss. The [research](researches/parallel-dependency-effects.researches.md) compared the removed `zipWith` branches with Cats Effect, ZIO, and Effect, and left the name, the release policy, and the reporting of extra failures open.
- Decision: A record of 2 to 8 `Dependency` values gains a `zipPar` getter beside `zip`, with the same shape. Its branches start together, keep their own step order, and yield the record in record order. The branches are not failure regions: a genuine branch failure completes the signal of the enclosing region at once, and the group waits until every branch settles before the rollback. The group owns one journal entry whose release starts every branch release at the same time, each branch in reverse order, with issues in reverse record order. The cause is the first genuine failure in record order; `branchFailures` on `ActivationException` and `ActivationCanceledException` keeps the others. `zip` stays sequential.
- Consequences: A component activates and releases its independent owned values in the time of the slowest branch. The runtime cannot check the independence of the branches; an interfering pair can leave external state unrestored, so the author MUST choose `zip` or a token key for shared state. `branchFailures` and `BranchFailure` extend the public exception model. The steps of one component no longer always run one at a time, so R-UC-RT-LC-005 gains an exception, the Down-set law becomes a rule over the partial order of completed effects with the chain as its sequential case, R-UC-RT-LC-002 and R-UC-RT-LC-021 release unordered branches at the same time, a branch starts only while the signal is not complete, the outcome follows the reason of the signal so a branch failure stays an `ActivationException`, and `OneStepPerNode` and the step order of `Cancellation.tla` hold only for nodes without a `zipPar` until a model extension covers the branches. G-RT-LC-008 stays open until the runtime implements the design. A shared prefix, bounded concurrency, and concurrent collection traversal stay out of scope.
- Supersedes: [Split a component into a source and its publications](#2026-11-06-decision--split-a-component-into-a-source-and-its-publications), only its rule that the steps of one component never overlap.
- References: [requirements](requirements.md), [spec](spec.md#composition-and-concurrency), [research](researches/parallel-dependency-effects.researches.md), [gap](gap.md).

## [2026-11-09] decision | Keep effect independence an author obligation stated as patterns

- Context: Module members, scope teardown, and `zipPar` branches overlap by default, so their effects must be independent (Definition 19). The [research](researches/effect-independence.researches.md) found that the paper already proves a key-level discipline (Theorems 40 and 42), and that a runtime check would need a commutativity classification of every shared key or declared footprints. A check stays conditional: Dart cannot confirm that a callback reaches shared state only through keys, and even Deterministic Parallel Java trusts its `commuteswith` declarations. The classification would add a concept to every shared key for a guarantee that remains conditional.
- Decision: The runtime does not classify keys, declare footprints, or check independence. Independence stays an author obligation. The package README states it as patterns: a `dispose` removes only its own contribution, shared global state has one owner, ordered uses of one resource share a token key, an update of shared state is not split at an `await`, and a publisher documents whether the operations of its value commute.
- Consequences: The API gains no new concept, and existing modules keep their concurrency. Interference is found by tests that vary completion order, not prevented by construction. The commutativity check stays an unaccepted candidate in the research; a later decision can adopt it if the patterns do not prevent interference. A review checks one step, one owner, or one published value at a time, instead of every overlapping pair.

## [2026-11-10] decision | Check internal invariants only inside assert, and keep misuse errors public

- Context: A random history finds a defect only through its public effect, far from the state change that caused it. - Decision: The runtime adds self-checks of internal invariants inside `assert` only, each with a test-only fault as a negative control. Public checks of misuse stay in every build. The cycle check stays public and skips its walk when the reading node has no readers.
- Consequences: Debug runs, the core suite, and the random histories check the invariants at the state change. Release builds pay nothing for self-checks. A test-only library under `src/` exposes the faults. The cycle check of a first `initialize` costs constant time per read.

## [2026-11-10] decision | Keep deliberate defects in the runtime behind assert

A defect covers only the histories that the harness can reach; a formal defect outside them, such as a read cycle, keeps no automatic evidence.

## [2026-11-10] decision | Do not depend on the zone of a finished call

- Context: A consumer app wrapped every `DiScope` call in a zone that schedules each microtask twice, on the caller zone and on the root zone. Under Flutter `testWidgets`, a `tearDown` that disposed a scope used by the body never finished. The body runs in a fake-async zone, and the binding runs the microtasks of that zone only while the body runs. `_Runtime.mutate` kept the gate of the last mutation and awaited it in the next mutation. The gate was a future of the zone of the last caller. A listener on a completed future, and the completion of a completer, run by a microtask of the zone that created the future. The same holds for the shared `Lazy` future, the waiter of `whenActive`, and the completer of a token. The reverse case also hung: a scope that the `setUp` created and the body used waited on a future of the real zone.
- Decision: The runtime does not wait on a future that an earlier call created, once the earlier call has finished. `mutate` counts open gates and awaits the last gate only while it is open; otherwise it awaits a fresh complete future of its own zone. `Lazy` shares a future only while the acquisition runs. A waiter of `whenActive` and of a token exists once for each zone. An operation that is still in flight when its own zone stops is out of scope. The runtime does not schedule work on the root zone and does not fork a zone around a user callback.
- Consequences: A consumer needs no dual-scheduling zone for calls that follow a finished call. A call that runs in a zone that never runs its microtasks again still cannot finish. The start of a mutation keeps one hop, but a mutation requested after a finished mutation and before the microtask that completes its gate starts one microtask later than before. The order of mutations, `ReentrantLifecycleError`, cancellation, and the delivery of errors are unchanged. `force` after a creation, and `whenCanceled`, return a new `Future` object each time. A token that nobody listens to schedules no completion microtask. The formal models take the queue as a FIFO and do not model the gate or the zone of a future, so they need no change. V-T-RT-LC-030 carries the evidence.
- Rejected: scheduling each microtask on the root zone as well, which hides a dead zone and runs a continuation outside the fake-async order; forking a zone around the action; a sync completer for the gate, which runs listeners inside the mutation.

## [2026-11-12] decision | Hold the state of the runtime as an immutable value, and call listeners at each transition

- Context: A listener received a `DiChange` for a commit, for the end of a release, and for a failure that no caller received. The creation of a node, the start of an activation, an activation that ended without a commit, the disposal of a node that was not active, `isInitialized`, and `isDisposed` changed with no call. No requirement stated what a `DiChangeKind` or `revision` means, and the reads of a node, the booleans of a scope, the change kinds, and `describe` each used other words for the same state. The Flutter adapter kept its own copy of each watched node and compared it at each change.
- Decision: The runtime is a state machine with three levels: a node, a scope, and the runtime of one root. Its state is an immutable value. `Scope.state` returns the `ScopeState` of a scope: its phase, a `NodeState` for each node, and the `ScopeState` of each child, so the value of the root is the state of the runtime. A transition replaces the state once, increases `revision` by one, and calls each listener of the root. A transition keeps the object of each node and of each scope that it does not change. A listener is a function without an argument that reads `Scope.state` and compares values, and `ScopeState.changedSince` gives the nodes that differ between two values. `DiChange`, `DiChangeKind`, and `DiListener` do not remain. The spec states the properties of the value, and the runtime MAY hold the value or compute it at a read.
- Consequences: One model states what a scope and a node are in: the reads agree with the value, and `describe` writes the same phases. A view keeps a `NodeState` and compares it with the next one, so it shows no stale state and keeps no copy of its own. `identical` tells that a scope did not change. One check over the random histories compares `Scope.state` with `revision`. Breaking change for every listener: it gets no argument, and a trace reads `changedSince` where it read a label from a change. V-T-RT-LC-029 is retired, and V-T-RT-LC-031 states the labels. A listener of any scope is called at every transition of the root. The creation of a child scope is a transition. `Scope.errors` reports a failure after the listener calls of its transition. The state holds no value of a node, no shape, no ancestor, and no resolved read.
- Alternatives: A change event for every transition, with new kinds and the state of the node in the event, keeps two models: the listener still reads the scope, and each kind needs its own delivery rule. A stream of states needs a controller, delivers after the transition, and adds a subscription to end; a function is enough. The state as the argument of the listener makes the runtime build a value at each transition. A link from a `ScopeState` to its parent gives every scope a new object at every transition of the root, so no object tells that a scope did not change, and a read of a small scope completes the value of the whole root. A parent that holds only the children that left `declared` loses a scope that initializes before its parent. A rewrite of the runtime as a pure function from a state and an event is not required for these properties, and it changes the code that the models and the random histories check. A copy of the shape in the state repeats a constant: the module does not change, and a tool joins the state with the `ShapeGraph` by position. Without `changedSince`, each trace compares two trees by hand.
- Supersedes: the change kinds of [Name the node in the change kinds and in the inactive exception](#2026-11-10-decision--name-the-node-in-the-change-kinds-and-in-the-inactive-exception).
- References: [requirements](requirements.md#r-uc-rt-lc-028), [state of the runtime](spec.md#state-of-the-runtime), the closed gap G-RT-LC-009, [change.dart](../../../packages/fp_di/lib/src/model/change.dart), [runtime_change_broadcaster.dart](../../../packages/fp_di/lib/src/runtime/runtime_change_broadcaster.dart).

## [2026-11-12] decision | Give a scope one phase for each state of its machine

- Context: A scope stated `isInitialized` and `isDisposed`, and the title of `describe` stated `(not initialized)`. No read told that `initialize` runs, although the scope has nodes in that time. A disposal has three steps: the accepted call, the start of the disposal mutation, and its end. A lookup answers after the first step and throws after the second.
- Decision: The scope machine has the states Declared, Initializing, Initialized, DisposeRequested, Disposing, and Disposed, and `ScopePhase` has one value for each. The phase `disposeRequested` starts at the accepted `dispose` call, for the scope and each descendant, and the phase `disposing` starts with the disposal mutation. A failed `initialize` returns the scope to `declared`, without nodes, only when the runtime accepted no `dispose` call before the rollback ended. Otherwise the rollback ends in `disposeRequested`, the value keeps the `disposed` nodes of the call, and the disposal mutation follows. `addListener` throws from `disposeRequested`. An accepted `dispose` call records its disposal before it calls the listeners.
- Consequences: Whether a lookup answers and what `isDisposed` returns are functions of the phase. A host reads that a scope initializes without a flag of its own. `isInitialized` stays true after a disposal, so the phase alone does not give it, and it stays a read of the scope. No scope leaves a phase of the disposal, so `isDisposed` does not return to false. A listener that calls `dispose` inside the accepted call joins that disposal. The start of the disposal mutation is one more transition.
- Alternatives: One phase `disposing` for DisposeRequested and Disposing hides a difference of the lookups inside one phase, and no transition tells when they start to throw. A lookup that throws from the accepted call makes one phase enough, and it changes when `get` fails. A phase `failed` after a failed `initialize` states a past event, and the caller of `initialize` has the failure.

## [2026-11-12] decision | Read the module of a scope with Scope.module

- Context: A scope kept its module in a private field. The state of the runtime holds no shape, and `nodes[i]` belongs to the component at position `i` of the module. A tool therefore needed its own reference to the module. A facade that builds a chain of child scopes, one for each installed module, could not read what a scope declares. `maybeNode` tells only that a key has a node. A declared key of a scope that is not initialized therefore reads like a key that no scope declares.
- Decision: `Scope.module` is a getter that returns the module of the scope, the same object at each read, in every phase. The module holds the declarations of that scope only. The reads of `Module` give the shape, and the scope gets no shape read of its own.
- Consequences: A caller joins `Scope.module.components` with `Scope.state.nodes` by position. `module.publishes` tells that a scope declares a key before the scope has a node of the key. A scope gives no handle of its parent, and a `ScopeState` holds no module. A caller that needs the declarations of an ancestor therefore holds that scope. The change adds one member, and no existing call changes.
- Alternatives: A static `Module.of(scope)` needs an import of `runtime/scope.dart` in `model/module.dart`. The [source folders of the core](../../architecture/spec.md#source-folders-of-the-core) forbid an import of `runtime/` from `model/`, and the audit of V-L-AR-DI-001 rejects it. ## [2026-11-13] decision | Select the members of a module that require absent keys

- Context: `initialize` throws `UndeclaredKeyError` for a member that requires a key that no declaration publishes. - Decision: `Module.requiring(keys:, ancestorKeys:)` returns the members that require a key of `keys`, directly or through the key of another member of the result. `Module.withoutRequiring` takes the same arguments and returns the other members.
