# Effect Independence and Key Commutativity

## Subject

The independence that fp_di requires of effects that run without an order, and
whether a key-level algebraic discipline can establish it instead of an author
assertion about every pair.

## Why

[Composition and concurrency](../spec.md#composition-and-concurrency) states
that authors MUST keep overlapping effects independent. Concurrent module
activation, concurrent teardown, and the `zipPar` branches rest on that
obligation. [Out of Scope](../requirements.md#out-of-scope) excludes a runtime
check of it. This note states the obligation precisely and records a candidate
discipline from the paper.

## Findings

### The obligation

Definition 8 (p. 12) defines a witnessed effect. Applied at state `γ`, it yields
a new state `δ` and an inverse `g` with `g(δ) = γ`. The witness constrains `g`
only at the state that the effect produced.

Definition 40 (pp. 26–27) defines the transformation monoid `𝔐(e)`. It is
generated by the forward map of `e` and every inverse that `e` yields.

Definition 42 (p. 27) calls `e1` and `e2` independent when both clauses hold, in
both directions:

1. Every transformation of one commutes with every transformation of the other:
   `f ∘ g = g ∘ f` for all `f ∈ 𝔐(e1)`, `g ∈ 𝔐(e2)`. This covers forward with
   forward, inverse with inverse, and forward with the other inverse.
2. No transformation of one changes the inverse that the other selects:
   `pr2(e1(g(γ))) = pr2(e1(γ))` for all `g ∈ 𝔐(e2)` and states `γ`.

Theorem 43 (p. 28) uses the definition. Under pairwise independence, an
inverse removes its own contribution at any later state. The inverses then
restore the initial state in any order. LIFO needs no independence (Theorem 16,
p. 15). Independence buys every other order and the interleaving of several
components.

Section 3.3.2 (pp. 23–25) reads all equalities up to an observational
equivalence `≃`. Two orders that no observer can tell apart count as commuting.

In fp_di terms, an effect is one `create` step with its `dispose`. The table
reads the clauses on common cases:

| Two effects | Clause 1 | Clause 2 | Independent |
|---|---|---|---|
| Each adds a listener and removes its own handle | Holds: the table answers every test alike in either order | Holds: each removal targets its own entry | Yes (p. 29 names this case) |
| Each opens a different file and closes it | Holds | Holds | Yes |
| Each sets one global config value and restores the value it saw | Fails: the final value depends on the order | Fails: the restored value depends on whether the other ran first | No |
| Each inserts a middleware into one ordered chain | Fails: the request passes the chain in a different order | — | No (p. 29 names this case) |
| One flushes a shared file, the other closes it | Fails: a flush after the close fails | — | No |
| Each allocates a handle, and handles are compared by equality | Fails: a further allocation separates the two orders | — | No (p. 29) |
| Each allocates a handle, and no operation compares handles | Holds up to a renaming of handles | Holds | Yes (p. 29) |

A Dart callback is not one atomic transformation. Another branch or member can
run at each `await`. Each segment between two `await` points is one step of the
interleaving. A read-modify-write that spans an `await` is two steps, and the
clauses apply to each step.

### Where fp_di relies on it

| Mechanism | Order that the runtime keeps | What independence must cover |
|---|---|---|
| Steps of one component | LIFO | Nothing (Theorem 16) |
| `initialize` of module members | Read edges between members | Members without a read path between them |
| `Scope.dispose` | Reverse read edges | Nodes without a read path between them |
| `zipPar` (proposed) | Order inside each branch | Steps of different branches |

Today the author asserts independence for every unordered pair. The runtime
cannot check the assertion. The number of pairs grows with the square of the
number of unordered nodes.

### The paper's discipline

Section 3.3.1 (pp. 21–22) binds every shared state to a coeffect key. "Every
interaction between a component and its environment passes through this single
entity."

Definition 29 gives each key `k` a coeffect `(𝒱k, 𝒜k)`: a value type and a set
of operations. The operations induce the equivalence `≃k` (Definition 31), and
Definition 46 adds a witness that the operations are pairwise independent.

Definition 44 (p. 28) calls a key commutative when any two of its operations
are independent.

Theorem 45 (p. 29) proves that operations at distinct keys are independent.

Definition 30 (p. 22) defines context-mediated iterators over the key sets
`P ⊆ S`. Such an iterator is a sequence of stages: an operation at a key of
`S`, where each argument may depend on earlier outcomes, or the provision of a
binding at a key of `P`.

Theorem 47 (p. 30) proves the discipline: two context-mediated iterators are
independent when neither provides a key at which the other operates
(`P1 ∩ S2 = P2 ∩ S1 = ∅`) and every key at which both operate is commutative.

The paper names one limit and one obligation:

- A location that the system cannot reify as a coeffect lies outside the
  theorem (p. 31).
- Commutativity concerns the operations of one key alone, "so the obligation
  falls on the component providing the key and on no component consuming it"
  (p. 29).

Non-commutative keys carry the order elsewhere (p. 30). Inside one component,
the accumulator imposes LIFO. Across components, a declared coeffect imposes
it: a provider precedes the readers of its key.

Section 4.3.2 (pp. 44–46) carries the result to interleaved fibers.
Definition 65 reads independence for iterators. Theorem 68 proves recovery
exactness. In v1 the results "assume nothing of the sequence" (p. 47): Lemma
66 derives pairwise independence from the witnesses of the components. The paper cites Mazurkiewicz trace
theory [46] for the reordering of adjacent independent steps.

The core theory is therefore already proved. The obligation moves from every
pair of effects to two local facts: each shared location has a key, and each
key's interface is honestly classified as commutative or not.

### Distance between the discipline and fp_di

- **Mediation.** A Dart callback can mutate globals, platform channels, files,
  and database internals without a key. The paper's hypothesis excludes such
  effects. fp_di cannot see them.
- **No commutativity attribute.** A `DiKey` carries a type and an instance name.
  It carries no classification of the interface that its value publishes.
- **Aliasing.** A value read at one key can hold a reference to the value of
  another key. A repository can hold the database that its publisher read. A
  component can then operate at a key that it does not read. The direct read
  set is not a sound footprint. The transitive closure of reads through
  publishers is sound when values flow only through keys.
- **Equivalence.** fp_di compares binding records by identity, as the paper
  mapping records. The discipline needs `≃k` only to justify a
  classification. The runtime never evaluates it.

### Example: two readers of one database

```text
Db ──> A
 └───> B
```

The read edges force `Db` before `A` and `B`, and release `A` and `B` before
`Db`. `A` and `B` have no read path between them, so they overlap. Both read
`Db`, so both may operate at the key `Db`. Theorem 47 applies when `Db` is
commutative. The discipline turns "are `A` and `B` independent?" into "is the
interface of `Db` commutative?". The publisher of `Db` answers that once.

### Collection keys as a structural case

The [collection keys](../spec.md#collection-keys) already reach the result of
the discipline for one shared structure, without a classification.

A registry to which many components add their own entry is the commutative
case that the paper names on p. 29: each adds a listener and removes its own
handle. A naive registry is one shared location. Its contributors would
operate at one key, and Theorem 47 would then need that key to be commutative.

The runtime reduces the registry instead. Each set contribution publishes
under an internal contribution key of its own. Each map entry publishes under
its entry key `map.entryKey(id)`. A collection read expands to plain reads of
those keys. The contributors therefore operate at distinct keys, and
Theorem 45 (p. 29) makes them independent. No key needs a commutativity
attribute, and no author can classify one wrongly.

The reduction also covers the ordered case. Insertion into an ordered chain
does not commute (p. 29), because the completion order would decide the
position. A collection value is not built by insertion. The runtime folds it
from the resolved publishers in an order that the declarations fix: ancestors
first, then declaration order. The completion order of the contributors
therefore does not change the value.

| Paper concept | Collection key |
|---|---|
| Commutative key: each operation adds or removes its own contribution | One key for each contribution; distinct keys are independent (Theorem 45) |
| Ordered key: insertion into an ordered chain | An order fixed by declarations; a fold over published values, not an insertion |
| Mediation: shared state passes through a key (§3.3.1) | The runtime owns the registry; contributors do not mutate it |

The reduction has two limits:

- It covers membership and the collection value only. A reader that calls
  methods of an element, or elements that share state outside the keys, fall
  under [the obligation](#the-obligation) again.
- Decoration, which the collection decision excludes, wraps one value in
  order: `d₂(d₁(v))`. It does not commute. A decoration key would need an
  order fixed by declarations, as the collection order is.

A set or map contribution resembles an op-based CRDT whose operations add and
remove only their own element. The [CRDT entry](#adjacent-work-verified-sources)
below states the commutativity condition that makes such operations
converge.

### Adjacent work (verified sources)

Databases, transactional memory, replication, and effect theory solve the same
problem: they derive safe concurrency from a commutativity specification of an
interface, and they undo with inverses. Each entry states its link to the
obligation above.

- **Transactional boosting.** M. Herlihy and E. Koskinen, *Transactional
  Boosting: A Methodology for Highly-Concurrent Transactional Objects*, Brown
  University Technical Report CS-07-08, July 2007. The PPoPP 2008 version
  (pp. 207–216, DOI `10.1145/1345206.1345237`) was not reachable; the report
  was read.
  - Conflicts come from the interface: "Two abstract locks conflict if their
    invocations do not commute" (p. 6).
  - Undo uses inverses: an aborting transaction "revisits the log entries in
    reverse order executing each inverse" (p. 6).
  - Rule 3 alone restores the state only "In the absence of any other
    concurrent transactions" (p. 13). Rule 2, "Commutativity Isolation", keeps
    non-commuting calls of two transactions ordered (p. 13). Theorem 5.3
    concludes strict serializability under these rules (p. 14).
  - Link: Rule 3 corresponds to Theorem 16 of the paper, and Rule 2 to the
    independence that Theorem 43 needs. A `dispose` plays the inverse, and an
    ordered key plays a conflicting abstract lock.
  - The method applies only to objects "where commutative method calls can be
    identified" and whose inverses exist (p. 6), so the classification is an
    input, as in Definition 44.
- **Sagas.** H. Garcia-Molina and K. Salem, *Sagas*, Princeton University
  CS-TR-070-87, January 1987, a scanned report read page by page. The SIGMOD
  1987 version (pp. 249–259, DOI `10.1145/38713.38742`) was not reachable.
  - Each step `Ti` has a compensating transaction `Ci`; the system runs either
    `T1 … Tn` or `T1 … Tj, Cj … C1` (pp. 2–3).
  - "The compensating transaction undoes, from a semantic point of view, any
    of the actions performed by Ti, but does not necessarily return the
    database to the state that existed when the execution of Ti began"
    (pp. 2–3).
  - "Ci cannot simply store in the database the number of seats that existed
    when Ti ran because other transactions could have run" in between (p. 3).
  - Link: the last quote is clause 2 of Definition 42. A `dispose` that
    restores a value saved by its `create` is the global-config row of the
    table above. The report leaves each `Ci` to the application, as fp_di
    leaves each `dispose` to the author.
- **CRDTs.** M. Shapiro, N. Preguiça, C. Baquero, and M. Zawirski,
  *Conflict-free Replicated Data Types*, SSS 2011, LNCS 6976, DOI
  `10.1007/978-3-642-24550-3_29`; the author copy hosted at Tufts was read.
  - Definition 6 (p. 6): two updates commute when each stays enabled after the
    other and both orders reach equivalent states.
  - "a sufficient condition for convergence of an op-based object is that all
    its concurrent operations commute" (p. 6). The state-based alternative is a
    monotonic semilattice whose merge is the least upper bound (Definition 4,
    Theorem 1, p. 5).
  - Link: a CRDT is a key whose every operation commutes, so it needs no order.
    The enabledness clause has no counterpart in Definition 42; it matters
    when a `create` has a precondition on shared state.
- **Effect-dependent optimisations.** O. Kammar and G. D. Plotkin, *Algebraic
  Foundations for Effect-Dependent Optimisations*, POPL 2012, pp. 349–360, DOI
  `10.1145/2103656.2103698`; the authors' preprint was read, so page numbers
  are preprint pages.
  - Effect annotations are sets of effect operations: "annotation effects can
    be identified with operation symbols" (abstract, p. 1).
  - "Swap corresponds to commutativity" (p. 10). The Swap example in Figure 7
    names "distinct global memory cells" (p. 9).
  - Theorem 13 (p. 10): the algebraic condition for Swap holds iff it holds
    for each pair of operations. Corollary 14 keeps it under a sum of theories.
  - Link: this is the type-system form of Lemma 41(1) and Theorem 47. A
    footprint of keys is an effect annotation, and the check per pair of
    operations is the check per key.
- **Deterministic Parallel Java.** R. L. Bocchino, *An Effect System and
  Language for Deterministic-by-Default Parallel Programming*, PhD
  dissertation, University of Illinois at Urbana-Champaign, 2010. It derives
  Chapter 3 from the OOPSLA 2009 paper (pp. 97–116), which was not reachable.
  - "the programmer partitions the heap using regions" and writes method
    effect summaries. The compiler checks "that parallel tasks are
    noninterfering (i.e., if any two parallel tasks access the same region,
    then all such accesses are operations that commute with each other, such
    as reads)" (Chapter 1, PDF p. 21).
  - `m commuteswith m'` declares that two methods may run in parallel
    regardless of their effects. "The commutativity property itself is not
    checked by the compiler" (§3.4, p. 43).
  - Link: the region check is the candidate shape check below. The trusted
    `commuteswith` is the residual obligation that a key's classification
    matches its interface.
- **Commutativity-based concurrency control.** W. E. Weihl,
  *Commutativity-Based Concurrency Control for Abstract Data Types*, IEEE
  Trans. Computers 37(12):1488–1505, 1988. The original was not read: DTIC
  refused automated fetches of MIT/LCS/TM-367, and IEEE requires a
  subscription. Herlihy and Koskinen state that "Weihl [34, 15] showed that
  commutativity can be used for concurrency control in distributed databases"
  (CS-07-08, p. 16). This note claims nothing about the original beyond that
  sentence.

### Related work (not re-read)

- Bernstein's conditions (A. J. Bernstein, IEEE Trans. Electronic Computers
  EC-15(5), 1966): two program segments may run in parallel when neither writes
  what the other reads or writes. This is a sufficient syntactic test of
  clause 1 for read/write footprints.
- Region-based effect systems (J. M. Lucassen and D. K. Gifford, POPL 1988;
  R. L. Bocchino Jr. et al., Deterministic Parallel Java, OOPSLA 2009):
  declared region effects let a checker reject interfering parallel blocks.
  A commutativity classification per key plays the role of a region effect.
- Concurrent separation logic (P. W. O'Hearn, Theoretical Computer Science 375,
  2007): disjoint ownership licenses parallel composition. It assumes that each
  command touches only its footprint, which corresponds to mediation here.

## Implications

### Outcome

The [decision of 2026-11-09](../log.md#2026-11-09-decision--keep-effect-independence-an-author-obligation-stated-as-patterns)
keeps independence an author obligation. The
[lifecycle notes](../../../../packages/fp_di/doc/lifecycle.md#effects-that-overlap)
of the package state it as patterns derived from the findings above. The candidate below
is not accepted. It stays as the reference design if guidance and tests do
not prevent interference. A parallel footprint proposal is in
[Footprint Independence](footprint-independence.researches.md).

### Candidate: a commutativity check derived from shapes

These obligations are a candidate, not an accepted contract.

- Classify each key as commutative or ordered. An ordered key publishes an
  interface whose operations do not commute.
- Derive a footprint for each node: the keys it reads, closed transitively
  through their publishers.
- Two effects are unordered when no read path connects their nodes, or when
  they are steps of two branches of one `zipPar`.
- Reject two unordered effects whose footprints share an ordered key. Reject
  them at `initialize` for members, and at construction for `zipPar` branches,
  whose shapes are static.
- Keep the keys the only order. The author resolves a conflict with a read
  edge, a token key, or `zip`. The runtime never adds a hidden order.
- Bind a shared location without a natural value to a token key that both
  components read, and classify that key as ordered. No new concept is needed.

With this check, Theorem 47 discharges independence for every pair that the
runtime overlaps. Theorem 43 and Theorem 68 then give recovery for concurrent
activation, concurrent teardown, and `zipPar`.

### Candidate: commutative structures as key kinds

This direction is a candidate, not an accepted contract. It complements the
classification check above.

- Offer a common shared structure as a key kind that the runtime reduces to
  distinct keys, as the [collection keys](#collection-keys-as-a-structural-case)
  do. Candidates are a registry, a counter, an ordered chain, and decoration.
- Fix each order by declarations, and build each value as a fold over
  published values.
- Leave the classification check for shared state that no key kind expresses,
  such as a database or a global setting.

A key kind gives independence by construction and needs no attribute. The
classification check covers the rest, and it relies on the author.

### Residual obligations

| Obligation | Scope | Discharged by |
|---|---|---|
| Each `dispose` is a witness of its `create` (Definitions 8 and 36) | One step | Author, as today |
| Each shared location is reached only through a key (§3.3.1) | One component | Author; outside the theorem otherwise |
| Each key's classification matches its interface (Definition 44) | One key, owned by its publisher | Author of the publisher |
| No unordered pair shares an ordered key | All pairs | Runtime check (candidate) |

The global pairwise obligation becomes three local obligations and one checked
property.

### Proof needs

| Item | Status | Means |
|---|---|---|
| Distinct keys are independent; shared commutative keys keep independence | Proved (Theorems 45, 47) | Reuse |
| Any inverse order restores the state under pairwise independence | Proved (Theorem 43) | Reuse |
| Recovery under interleaving | Proved for the paper's fibers (Theorem 68) | Reuse; fp_di has no refinement proof to that semantics |
| The check covers every pair that the scheduler can overlap | New | TLA invariant over `Initialize.tla`, `Teardown.tla`, and a `zipPar` extension |
| The transitive read closure over-approximates the keys at which a node operates | New, under the mediation assumption | Pen-and-paper lemma; optionally Lean |
| An `await` segment of a Dart callback maps to one step of the paper's trace | Open | Part of the existing refinement boundary of the [formal spec](../../../verification/formal/spec.md) |

## Open Questions

- Choose the default for an unclassified key. Commutative keeps current
  behavior and checks nothing. Ordered is safe but serializes most of an
  application.
- Choose where the classification lives: on a `DiKey` instance, on the value
  type, or on the publishing component.
- Decide whether a reader that only queries a key needs a separate read form.
  Without one, every reader of an ordered key conflicts with every other.
- Decide whether a conflict fails `initialize`, or only appears in the shape
  export and `describe()`.
- Decide whether the check spans separately initialized scopes, whose nodes the
  mutation queue serializes but whose effects can still interleave.
